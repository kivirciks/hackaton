# Архитектура прототипа и границы интеграции

## Поток данных

`archive.py` читает предоставленные 7z, `pipeline.py` агрегирует сигналы по дню/объекту/системе, `model.py` обучает и оценивает прогноз **нового тревожного дня**, `server.py` показывает готовый `forecast.csv`. `service.py` обслуживает локальные журналы, дерево, роли, эмуляцию и уведомления. `reports.py` формирует управленческий и аудиторский срез одним запросом к SQLite. `scheduler.py` и `operations.py` выполняют версионированный ingest, проверку качества, резервирование и измерения.

Путь к интерфейсу после запуска: `http://127.0.0.1:8080`. При первом запуске создаются учетные записи `dispatcher` и системная `admin` с паролем `demo`, а также роль `dispatcher`. Остальные роли и логины создает администратор через страницу «Роли и доступ» или API. Встроенная роль администратора неизменяема и имеет все права. Это механизм локального демо на localhost; в промышленной сети требуются IdP/AD, TLS, сессионное хранилище и управление секретами.

## Роли и охват

| Участник | Доступ при первом запуске | Запись |
| --- | --- | --- |
| Диспетчер | Прогнозы, условная схема, оборудование, отчеты и статус локальной заявки | Решение, черновик, локальное оборудование, просмотр оповещения |
| Системный администратор | Все страницы, включая «Поступление данных» и «Роли и доступ» | Управление ролями и логинами, сверка реестра, исторический поток, прочее |
| Созданная администратором роль | Выбранные администратором разрешения; например, `reports:read` для аудитора | По назначенным разрешениям |

`GET /api/roles` возвращает каталог разрешений, роли и учетные записи без хешей паролей. `POST /api/roles` сохраняет роль, `POST /api/users` создает/обновляет учетную запись и при необходимости пароль. Эти пути доступны только системному администратору; служебные права `roles:manage`, `stream:write`, `objects:write`, `registry:sync` и `audit:read` нельзя передать обычной роли. Право по умолчанию отсутствует. Каждая API-операция проверяет сессию и текущий список прав из SQLite, поэтому отзыв права применяется без повторного входа; POST требует CSRF токен. Ограничения доступа к веткам `object_id` в этом прототипе пока нет: `allowed` применяет право роли, но не отдельный список объектов. Это нужно согласовать и реализовать перед эксплуатацией.

Записи аудита связаны SHA-256 и SQL триггерами защищены от UPDATE/DELETE; администратор базы всё ещё может заменить БД, поэтому нужны внешнее WORM хранилище, подпись и сроки хранения.

## Контракт заявок v0 (на согласование заказчику)

| Шаг | Локальный API | Смысл |
| --- | --- | --- |
| Черновик | `POST /api/tickets/drafts` | `object_id`, `equipment`, `reason`, `priority` (`обычный`, `высокий`, `критический`), `due_at` (`YYYY-MM-DD`). Ответ `id`, `status=draft`, `external_sent=false`. |
| Подтверждение | `POST /api/tickets/{id}/confirm` | `{"confirm":true}`; сохраняет `confirmed_locally`, **не отправляет** внешнюю заявку. |
| Чтение статуса | `GET /api/tickets/{id}` | `external_status=НЕДОСТУПЕН — ДЕМО-ЗАГЛУШКА`, `source=stub`, локальный черновик при наличии. |

Для реального адаптера нужны: адрес и протокол API, OAuth/mTLS, стабильные ID объекта и оборудования, справочник причин/приоритетов, формат срока и часовое пояснение, код ответа, статусная модель, идемпотентный ключ, таймауты, ошибки и договор о доступе **только на чтение** для статуса. Отправка заявки — отдельное согласование после ручного подтверждения и маппинга ID.

## Поток и карта

Эмуляция берет последние 7 доступных дат из `daily.csv`, сохраняет исходный день и новые времена приема/обработки в `stream_events`. Идемпотентный ключ `(source_at, object_id, category)`; до трех попыток при блокировке SQLite. Активный сигнал уведомляет по историческим значениям; прогнозное уведомление применяется только к совпадающему дню прогноза. Дедупликация `(object_id, category, source_day)`. Интерфейс опрашивает API каждые 5 секунд, квитирование сохраняется. Для промышленного потока нужны брокер, watermark по времени источника, DLQ, отдельные clocks и p95 сквозной задержки.

SVG схема создается в браузере по ID и иерархии объектов. Элементы одного родителя объединены рамкой площадки и расположены рядом; участки с обозначением `ПК` упорядочены по номеру только внутри своей площадки. Фильтр категории использует точное значение `тип_инж_системы` справочника каналов; цвет отражает наиболее важный статус объекта по всем модельным системам. Координат, адресов и направлений в источнике нет, поэтому рамки и расстояния не являются картой Москвы. Красный означает тревожный сигнал датчика, оранжевый — прогноз выше порога, зеленый — наблюдение при поступающих данных, серый — нет или мало данных. Цвет не подтверждает поломку или исправность; элемент открывает карточку либо реестр.

## Отчеты и аудит

`GET /api/reports?kind=...&from=YYYY-MM-DD&to=YYYY-MM-DD` поддерживает `management`, `forecast`, `activity`, `quality`, `audit`; фильтры `object_id`, `system`, `status`, `min_score` (процент, 0–100) применяются там, где поля осмысленны. Экспорт `reports.xlsx` / `reports.pdf` использует тот же срез: в Excel листы «Данные» и «Параметры и методика». Для локальных действий даты означают период **создания** записей; `forecast` и `quality` показывают один исторический снимок. `metrics.json` — метрика фиксированного исторического теста. Если администратор создаст аудитора с одним правом `reports:read`, он увидит только страницу отчетов и сможет выбрать `audit` для журнала действий; отдельный `GET /api/audit` доступен только администратору.

## Регулярные процессы и границы приемки

`python -m collector_risk.scheduler --source upload --artifacts artifacts --utc-time 23:59` выполняет ежедневный запуск по UTC; предпочтительнее планировщик OS с `--once`. `operations.refresh` считает SHA-256 источников, сохраняет `versions/<hash>/` и проверяет уникальность ключа, даты, счетчики. Новая модель проходит временной тест и грубый порог снижения average precision; неизменный контрольный период и мониторинг качества по подтвержденным исходам требуется согласовать отдельно. Файл подтверждений (`object_id,incident_type,occurred_at,confirmed_by`) сохраняется для анализа; модель тревог не объявляется моделью подтвержденных аварий.

`scheduler` после успешного ежедневного цикла делает копию в `artifacts/backups/YYYY-MM-DD` и проверяет ее восстановление. `operations backup` позволяет сделать внеплановую консистентную копию SQLite и артефактов; `verify-backup` сверяет хеши и пробует восстановить БД во временную папку. Шифрование, сроки хранения и удаленное хранилище остаются обязанностью целевой инфраструктуры. `operations benchmark` и `load_test` дают воспроизводимые локальные p95/p99; целевые SLA ≤300 с, ≤5 минут и 20 пользователей требуется повторить на целевом Linux с боевой нагрузкой и реальным входным потоком.
